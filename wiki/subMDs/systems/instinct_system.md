## 1. Why the LLM gets generated behavior primitives

### 1.1 The problem the flat action list creates

The LLM agent today receives a **flat vocabulary of atomic actions** and must plan multi-step behavior itself: to fight, a weak local model (tight per-call time budget, small `max_tokens`, one retry — llm_turns_npc_spec §6.5) must emit two correctly-parameterized tool calls in the right order, recovering every parameter from the raw context. Each extra tool call is another chance for a malformed argument, a wrong id, or a wasted retry. The existing chase-then-attack behavior in the deterministic brain ([`NpcAIController.js`](../../src/controllers/ai/NpcAIController.js)) proves the *behavior* is valuable; the LLM path just cannot express it compactly.

### 1.2 What an instinct is

An **instinct** is a high-level behavior whose **name and action list are generated by code at runtime** from the action registry and the entity's live capabilities — never hardcoded fixed strings (not in `data/`, not in the prompt). The LLM calls the instinct; the server does the actions:

- **Stable high-level vocabulary.** The name is a function of *which behavior roles the entity can perform*, not of volatile stat values. The model learns a small, stable verb set instead of re-deriving multi-step plans each round.
- **Less per-action micromanagement.** One tool call replaces two parameter-heavy calls; the server resolves all parameters (target, direction, source/target components) deterministically.
- **Single source of truth = the action registry.** Instinct content is *derived* from the action registry + the capability cache. Add or remove an action in the registry, and the instinct vocabulary evolves automatically — no prompt edits, no data-file instinct lists.
- **Server stays authoritative.** Consistent with "the model proposes, the world disposes": the model chooses *what* (instinct + optional target); the server owns *how* (parameter resolution, ordering, validation, dispatch through the existing pipeline).

### 1.3 Why a hybrid tool and not more data

The alternative — describing multi-step behavior in the action registry data — would mix runtime-capability logic (which of two movement actions this body can do *right now*) into static data, and would still force the LLM to emit multiple tool calls. A **new LLM tool** keeps the small-tool-count discipline (small local models are reliable with few tools), reuses the entire existing validation/dispatch pipeline, and costs the model one extra enum to learn.

## 2. Architecture (Why This Shape)

### 2.1 A stateless logic controller

Instinct generation and expansion both must read the **live facade** (capability gate, entity positions, action registry), so the new `InstinctController` is a **stateless logic controller**: it owns no game state, exposes no bulk state getter, and is a pure function of injected state read through the facade. A stateless utility module would have to be handed facade data on every call, leaking capability/registry internals to each caller — a logic controller is the shape that reads world state through the facade by design.

Placement rationale:

| Question | Answer | Why |
|---|---|---|
| Controller or util? | **Logic controller** | Generation/expansion read live facade state (capability gate, positions, registry). A util would leak those internals to every caller. |
| Which directory? | **`controllers/ai/`** | It is NPC *behavior* logic — the LLM-side twin of the deterministic brain's behavior registry. It is **not** LLM transport (`networking/`): it never talks to a model. Keeping it in `ai/` leaves it reusable by the deterministic brain later. |
| State owner or not? | **Not** | Instincts are regenerated per round from live state; there is nothing to persist or broadcast. Hence **no persistence schema change and no broadcast entry**. |
| Who constructs it? | **Composition root** | Per Controller Patterns, logic controllers are built in the composition root and the facade is injected afterwards via a setter. It is stored on the facade as a reference but **not** added to the broadcast map. |

### 2.2 Why generation is live and uncached

Generation is **recomputed live, once per round**, from a single capability snapshot. The agent generates once and threads the result both into the context build and the tool enum — no second generation, no cross-round cache. A cache would risk serving stale capabilities; the capability engine already caches the expensive part, so the instinct layer adds no new scoring code and reuses the one scoring authority rather than introducing a second.

### 2.3 Why names are stable (design intent)

The instinct *name* is the vocabulary the model learns, so it is designed to churn as little as possible:

- **The name is a truthful summary of capability, not of outcome.** It is composed from *which behavior roles resolve*, never from *which specific action wins the ranking* or from numeric stat values. A knife losing sharpness (but staying above threshold) changes nothing; the knife breaking swaps the attack action **without renaming**; a merchant whose strength is below the punch threshold never shows an `…_attack` name. The model's learned vocabulary churns only when a whole capability class appears or disappears.
- **Omission, not placeholder.** A role with no executable candidate contributes nothing to the name — the name never promises what the body cannot do. A model that calls a chase-attack name is guaranteed an attack step will be attempted.
- **Collision safety.** Generated names must be unique within the NPC's instinct set and must not equal a literal action name, keeping the two tool vocabularies unambiguous for weak models.

## 3. Execution Semantics (Why)

- **One call, full sequence, same round.** An instinct call expands to the complete ordered sequence at dispatch time, and each step is queued as its own entry so the turn system executes the actor's entries in FIFO order — the move lands before the attack in the same resolution pass.
- **The turn system stays semantically ignorant of chains.** It owns timing and ordering only. If a move fails at resolution, the queued attack still runs and fails its own range check rather than being cascade-cancelled — both failures reach the LLM as separate tagged feedback entries, which is exactly the signal it needs to adapt next round (dash instead of move, or attack directly when in range).
- **Feedback is tagged per instinct.** The queued steps are separate outcomes; a small per-outcome tag is what tells the model *why* they happened together ("my chase-attack closed with the punch out of range") — the information that breaks action loops (llm_agent_action_feedback_plan root symptom).
- **Explicit targets fail loudly.** Only an *absent* target defaults to "nearest entity in room"; an explicitly supplied target that is invalid fails with a matching error code, so the model's mistake is not silently papered over.
- **Parameters are frozen at expansion; positions are live at resolution.** A target that drifts between planning and resolution can legitimately take an attack out of range — documented and accepted, because the LLM re-decides next round with fresh context.

## 4. Non-goals

- **No `NpcAIController` behavior change** — the deterministic brain keeps its own hardcoded behavior registration; the instinct design is *reusable* by it later, but out of scope.
- **No new data files** — and no instinct strings or action-name lists in any existing data file. Templates and role naming live in code.
- **No client/UI changes** — instincts are server-internal; queued steps surface in the turn state like any action.
- **No changes to the existing LLM tool contracts**, to the LLM transport controller, to routes, or to the action pipeline.
- **No persistence schema change** — instincts are regenerated per round; there is no instinct state to persist (the feedback store's instinct tag is ephemeral by design).
- **No multi-target or branching instincts** — a template is a linear chain of single-target steps.

## Appendix A — Concrete effect on the current world

- **The shipped merchant NPC** (the only LLM NPC): its strength is below the punch threshold, it carries no knife and no T1 weapon, and both basic movement actions are executable at equal capability scores. The generated instinct is therefore a **move-only `chase`** — "move toward the target." One tool call, zero micromanagement, and a name that honestly says it never attacks.
- **Any NPC with enough strength**: a full `chase_attack` — move then punch; with an equipped sharp knife the attack role can rank the cut instead — same name, same call, different body.
- **Player droid / deterministic NPCs:** unaffected (non-goal).

*End of specification.*
